# CODEX RULES — ПРОЕКТ «ВСЁПОНЯТНО»

Версия: 1.1  
Среда: PROD / stage  
Стек: WordPress + Directus + PostgreSQL + Redis + 3D converter

## 1. Общие правила ответа

1. Summary писать на русском языке.
2. Если меняется файл — выводить полный файл целиком.
3. Не выводить diff-патчи, если пользователь явно не попросил diff.
4. Не использовать CRLF. Только Unix LF.
5. Не вставлять пояснения внутрь кода или внутрь итогового файла.
6. Комментарии к изменениям писать отдельно от содержимого файла.
7. Сначала давать план, потом изменения, потом команды, потом проверки.
8. Если факт можно проверить по репозиторию, docs или snapshot — не фантазировать.

## 2. Архитектурные ограничения

Без прямого указания нельзя менять:
- mu-plugin proxy и token flow;
- `/scan`;
- service-worker;
- manifest;
- Nginx конфиги;
- Docker конфиги;
- ENV-файлы;
- глобальные WordPress hooks.

Нельзя:
- удалять рабочую логику;
- менять API контракт без запроса;
- менять Directus schema без запроса;
- ломать безопасность авторизации;
- уводить фронт на прямой Directus access.

## 4. Текущие продуктовые принципы

- `/scan` — входная точка.
- `/instruction` — универсальная страница для instruction-oriented сценариев.
- `/3d` — отдельная страница для 3D / navigation viewer-сценариев.
- Browser ходит только в WordPress.
- WordPress ходит в Directus server-to-server.
- Токены и protected file flow не уходят в браузер.

## 5. Стиль кода

### PHP
- отступы 2 пробела;
- без closing `?>`;
- `function_exists` перед объявлением функций, если это уместно для MU-plugin среды;
- без вывода секретов в логи.

### JS
- IIFE или `DOMContentLoaded`;
- без глобальных переменных вне допустимого namespace;
- без inline eval;
- не ломать существующие страницы.

### CSS
- аккуратные изолированные стили;
- не ломать базовую сетку темы;
- не переписывать глобальный UI без запроса.

## 6. Правила изоляции

Новые функции должны быть:
- минимальными;
- обратимыми;
- изолированными;
- ограниченными нужной страницей или нужным endpoint.

Новые скрипты подключать:
- только там, где они нужны;
- без глобального воздействия на весь сайт;
- без риска для `/scan`, `/instruction` и onboarding admin.

## 7. 3D engine правила

- `model-viewer` подключать только как ESM `<script type="module">`.
- Не подключать CDN.
- Не дублировать подключение viewer.
- Ждать `customElements.whenDefined('model-viewer')`.
- Не ломать protected file flow.
- В Redis очередь класть `vp_3d_jobs.id` как integer, не UUID файла.

## 8. PWA правила

- не менять service worker стратегию без отдельной задачи;
- не ломать version-busting;
- не ломать оффлайн-режим;
- не менять manifest без отдельной причины.

## 9. Directus правила

- не выдумывать поля, которых нет в snapshot;
- не описывать integer ID как uuid;
- не менять роли и политики без запроса;
- не менять snapshot без запроса;
- при генерации кода опираться на реальные коллекции и реальные поля.

## 10. Формат рабочего ответа

В нормальной инженерной задаче ответ должен содержать:
1. краткий план;
2. список файлов;
3. полный файл или файлы;
4. команды для сервера;
5. git-команды;
6. проверки и риски.

## 11. Основной принцип

Проект работает на продакшене. Любое изменение должно быть:
- предсказуемым;
- минимальным;
- безопасным;
- проверяемым;
- согласованным с текущими docs и snapshot.
